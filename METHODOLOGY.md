# Методология проведения сравнительных экспериментов

## Обзор

Данный документ описывает методологию проведения сравнительных экспериментов по генерации автоматических тестов с использованием различных LLM моделей через OpenRouter API.

## Архитектура процесса

Эксперимент состоит из четырех основных этапов:

1. **Генерация тестов** - создание тестовых файлов с помощью LLM
2. **Запуск тестов** - выполнение сгенерированных тестов
3. **Оценка результатов** - анализ качества и корректности тестов
4. **Генерация отчетов** - создание сравнительных отчетов

---

## Этап 1: Генерация тестов

### Команда запуска

```bash
# Генерация одного теста
npm run generate:test -- --model <model> --type <unit|integration|e2e> --target <target>

# Генерация всех тестов для типа (для множества моделей)
npm run generate:all -- --type <unit|integration|e2e>
```

### Что передается LLM модели

#### Системный промпт

Системный промпт определяет роль и требования к генерации:

```
You are an expert test engineer specializing in generating comprehensive test suites for web applications.

Your task is to generate high-quality test code following best practices:
- Use appropriate testing frameworks (Jest, React Testing Library, Playwright, Supertest)
- Write clear, maintainable, and well-documented tests
- Cover both happy paths and edge cases
- Use data-testid attributes for element selection
- Follow the test specification provided
- Generate complete, runnable test files
- IMPORTANT: Use correct import paths based on test file location
- Generate the COMPLETE file - ensure all test cases are fully implemented
```

#### Пользовательский промпт

Пользовательский промпт формируется динамически и включает:

1. **Исходный код тестируемого компонента/модуля**
   - Загружается из файловой системы
   - Для unit тестов: `FeedbackForm.jsx`, `FeedbackList.jsx`, `validation.js`
   - Для integration тестов: `server/index.js`
   - Для E2E тестов: соответствующие компоненты

2. **Спецификация тестов** (`TEST_SPECIFICATION.md`)
   - Описание структуры приложения
   - Категории тестов (unit, integration, e2e)
   - Сценарии тестирования
   - Требования к покрытию
   - Список `data-testid` атрибутов

3. **Руководство по генерации** (`TEST_GENERATION_GUIDE.md`)
   - Структура директорий для тестов
   - Целевые файлы для генерации
   - Правила импортов
   - Примеры использования фреймворков

4. **Информация о путях импорта**
   - Критически важно для корректности тестов
   - Для `components/__tests__/`: `import X from '../Component'`, `import Y from '../../utils/module'`
   - Для `utils/__tests__/`: `import X from '../module'`
   - Для E2E: стандартные импорты Playwright

5. **Требования к генерации**
   - Полный файл с закрывающими скобками
   - Корректные пути импорта
   - Использование правильных фреймворков
   - Покрытие всех сценариев из спецификации

### Параметры генерации

- **Temperature**: 0.7 (по умолчанию), настраивается через `--temperature`
- **Max Tokens**: 8000 (по умолчанию), настраивается через `--max-tokens`
- **Retry Logic**: автоматический повтор при rate limiting (до 3 попыток)

### Сохранение результатов

Сгенерированные тесты сохраняются в структуре:

```
research-output/
  <model-name>/
    <test-type>/
      <test-file-name>
      <test-file-name>.meta.json  # Метаданные генерации
```

**Метаданные включают:**
- Имя модели и ID
- Тип теста и целевой компонент
- Параметры генерации (temperature, maxTokens)
- Время генерации (TTG - Time To Generate)
- Timestamp генерации

### Поддерживаемые модели

- **Платные**: GPT-4, Claude 3.5 Sonnet, Gemini Pro, и др.
- **Бесплатные**: Llama 3.2 3B, Llama 3.1 8B, Qwen 2.5 7B
- **Динамический список**: можно получить через `npm run list:models`

## Этап 2: Запуск тестов

### Процесс выполнения

Скрипт `evaluate-tests.js` выполняет следующие шаги для каждого сгенерированного теста:

#### 1. Проверка существования файла
- Проверка наличия тестового файла
- Загрузка метаданных (если есть)

#### 2. Проверка синтаксиса
- Удаление markdown code blocks (если есть)
- Базовая проверка структуры кода
- Подсчет тестовых случаев (`test()`, `it()`, `describe()`)

#### 3. Копирование теста в рабочую директорию

Тесты копируются в соответствующие директории проекта:

- **Unit тесты**:
  - Компоненты → `client/src/components/__tests__/`
  - Утилиты → `client/src/utils/__tests__/`

- **Integration тесты**:
  - API → `server/__tests__/`
  - Утилиты → `server/utils/__tests__/`

- **E2E тесты**:
  - → `tests/e2e/`

#### 4. Модификации для E2E тестов

- Замена `localhost` на `127.0.0.1` (избежание IPv6 проблем)
- Инъекция coverage fixture (если включено покрытие)
- Замена импорта `@playwright/test` на `test-with-coverage.js`

#### 5. Вычисление baseline покрытия (опционально)

Перед запуском теста вычисляется покрытие **без** этого теста:

- Временное переименование тестового файла
- Запуск всех остальных тестов с coverage
- Сохранение baseline покрытия
- Восстановление файла

#### 6. Запуск теста

**Unit тесты:**
```bash
cd client && npm test -- --testPathPattern="<filename>" [--coverage]
```

**Integration тесты:**
```bash
cd .. && npm run test:server -- --testPathPattern="<filename>" [--coverage]
```

**E2E тесты:**
```bash
npx playwright test <filename> [--reporter=json]
```

#### 7. Парсинг результатов

Извлекается информация:
- Количество пройденных тестов (`passCount`)
- Количество упавших тестов (`failCount`)
- Общее количество тестов
- Статус выполнения (`passes: true/false`)
- Ошибки выполнения

#### 8. Вычисление покрытия кода (опционально)

Если включено покрытие (`COMPUTE_COVERAGE=1`):

- Чтение coverage отчетов (JSON summary)
- Вычисление покрытия для исходного файла
- Вычисление delta покрытия: `coverageDelta = coverageGenerated - coverageBaseline`

**Для E2E тестов:**
- Использование Playwright Coverage API
- Обработка coverage файлов из браузера
- Агрегация покрытия по нескольким запускам

#### 9. Обработка flaky тестов

По умолчанию тесты запускаются **3 раза** (`FLAKY_RUNS=3`):

- Первый запуск: с вычислением покрытия
- Последующие запуски: без покрытия (для скорости)
- Агрегация результатов по всем запускам

#### 10. Сохранение логов

Все выводы тестов сохраняются в:
```
<test-directory>/.eval-logs/<test-file>.jest.log
<test-directory>/.eval-logs/<test-file>.playwright.log
```

## Этап 3: Оценка результатов

### Метрики оценки

Для каждого теста собираются следующие метрики:

#### Базовые метрики

- **exists**: файл существует
- **syntaxValid**: синтаксис валиден
- **runs**: тест запускается без критических ошибок
- **passes**: все тесты проходят
- **testCount**: количество тестовых случаев
- **passCount**: количество пройденных тестов
- **failCount**: количество упавших тестов

#### Метрики покрытия (если включено)

- **coverageBaseline**: покрытие до добавления теста
- **coverageGenerated**: покрытие после добавления теста
- **coverageDelta**: прирост покрытия
- **coverageSourceFile**: исходный файл, для которого вычисляется покрытие

#### Метрики производительности

- **ttgSeconds**: время генерации теста (из метаданных)
- **errors**: массив ошибок и предупреждений
- **logPath**: путь к логу выполнения

#### Дополнительные метрики

- **rootCause**: основная причина неудачи (если есть)
- **model**: имя модели, сгенерировавшей тест
- **type**: тип теста (unit/integration/e2e)
- **file**: путь к тестовому файлу

### Агрегация результатов

Результаты группируются по:
- Модели
- Типу теста
- Целевому компоненту

Вычисляются статистики:
- Процент успешных тестов
- Среднее покрытие
- Средний прирост покрытия
- Среднее время генерации

## Этап 4: Генерация отчетов

### Формат отчета

Отчет сохраняется в JSON формате:
```
research-output/evaluation-report.json
```

### Структура отчета

```json
{
  "timestamp": "ISO timestamp",
  "summary": {
    "totalTests": 100,
    "successfulTests": 85,
    "failedTests": 15,
    "successRate": 85.0,
    "averageCoverage": 75.5,
    "averageCoverageDelta": 12.3
  },
  "byModel": { ... },
  "byType": { ... },
  "byTarget": { ... },
  "results": [ ... ]
}
```

### Визуализация отчета

Команда `npm run show:report` отображает:

1. **Общая статистика**
   - Общее количество тестов
   - Процент успешных
   - Среднее покрытие
   - Средний прирост покрытия

2. **Статистика по моделям**
   - Таблица с метриками для каждой модели
   - Сортировка по успешности/покрытию

3. **Статистика по типам тестов**
   - Unit vs Integration vs E2E
   - Сравнение метрик

4. **Детальные результаты**
   - Список всех тестов с их статусами
   - Ошибки и предупреждения
   - Ссылки на логи

### Цветовая индикация

- 🟢 **Зеленый**: успешные тесты, высокое покрытие (≥90%)
- 🟡 **Желтый**: среднее покрытие (70-89%)
- 🔴 **Красный**: неуспешные тесты, низкое покрытие (<70%)

## Полный цикл эксперимента

### Пример команды

```bash
# 1. Генерация тестов для всех моделей
npm run generate:all -- --type unit

# 2. Оценка сгенерированных тестов
npm run evaluate:tests

# 3. Просмотр отчета
npm run show:report
```

### Переменные окружения

- `FLAKY_RUNS=3` - количество запусков для flaky тестов
- `COMPUTE_COVERAGE=1` - включить вычисление покрытия
- `EVALUATION_COVERAGE=1` - альтернативное имя для покрытия
- `DEBUG_COVERAGE=1` - отладочный вывод для покрытия

## Особенности реализации

### Обработка ошибок

- **Rate Limiting**: автоматический retry с ожиданием
- **Синтаксические ошибки**: детектирование незакрытых скобок
- **Buffer Overflow**: использование временных файлов для больших выводов
- **Network Errors**: graceful degradation

### Оптимизации

- **Параллельная обработка**: тесты могут обрабатываться параллельно
- **Кэширование**: baseline покрытие вычисляется один раз
- **Временные файлы**: очистка после использования

### Расширяемость

- Легко добавить новые модели через OpenRouter API
- Поддержка кастомных промптов
- Гибкая конфигурация метрик оценки

## Выводы

Данная методология обеспечивает:

1. **Стандартизацию**: единый процесс для всех моделей
2. **Автоматизацию**: минимальное ручное вмешательство
3. **Сравнимость**: одинаковые условия для всех моделей
4. **Детальность**: глубокий анализ качества тестов
5. **Воспроизводимость**: сохранение всех метаданных и логов

Это позволяет проводить объективное сравнение различных LLM моделей в задаче генерации автоматических тестов.
