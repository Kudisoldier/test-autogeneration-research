# Отчет о проделанной работе по практике

## 1. Введение

В рамках прохождения практики была выполнена задача разработки практического решения по теме автогенерации тестов для веб-приложений с последующей контейнеризацией и поставкой в CI/CD-конвейер.  
Актуальность темы обусловлена тем, что рост функциональности современных web-систем приводит к быстрому увеличению объема регрессионных проверок. Поддержка тестов вручную становится трудоемкой, а для исследовательских задач требуется возможность быстро сравнивать разные подходы к генерации тестов в одинаковых условиях.  
В связи с этим в проекте была реализована единая воспроизводимая среда, которая объединяет:

- тестовый стенд (frontend + backend приложение);
- механизм автогенерации тестов;
- процесс выполнения и оценки тестов;
- систему автоматизации сборки, публикации и сохранения артефактов.

В качестве базовых технологических ориентиров использованы:

- Docker и Docker Compose для упаковки и воспроизводимого запуска [1], [2];
- GitHub Actions для автоматизации CI/CD и артефактов [3], [4];
- Node.js/npm как среда исполнения [5], [6];
- Jest, Testing Library и Playwright как инфраструктура тестирования [7], [8], [9];
- OpenRouter API как шлюз доступа к LLM-моделям для генерации тестов [10].

## 2. Цель, объект, предмет и задачи практики

### 2.1. Цель работы

Разработать и внедрить практическое решение для автогенерации и оценки тестов веб-приложения, обеспечив:

- воспроизводимость запусков;
- контейнеризацию среды;
- автоматизацию ключевых операций через CI/CD;
- сохранение и анализ результатов экспериментов.

### 2.2. Объект и предмет исследования

- **Объект исследования:** процесс тестирования веб-приложения.
- **Предмет исследования:** методы и средства автогенерации тестов, а также организационно-технические механизмы их запуска, оценки и публикации результатов.

### 2.3. Задачи практики

1. Проанализировать возможные варианты практической реализации автогенерации тестов.
2. Спроектировать состав решения: тестовый стенд, генератор, среду запуска, систему сбора артефактов.
3. Реализовать контейнеризацию практического решения.
4. Настроить CI/CD-конвейер для проверки, сборки и публикации.
5. Организовать процесс генерации, запуска и оценки автогенерированных тестов.
6. Подготовить подробную документацию по развёртыванию и эксплуатации.

## 3. Проектирование развертывания практического решения

### 3.1. Варианты практической реализации

На этапе проектирования были рассмотрены три варианта:

1. **Локальный запуск без контейнеров.**  
   Преимущество: минимальный порог входа.  
   Недостатки: различия окружений, сложность воспроизводимости, высокий риск дрейфа зависимостей.

2. **Контейнеризация без CI/CD.**  
   Преимущество: воспроизводимая среда выполнения.  
   Недостатки: отсутствие системной автоматической проверки изменений и единых артефактов.

3. **Контейнеризация + CI/CD (выбранный вариант).**  
   Преимущества: воспроизводимость, автоматический контроль качества, централизованное хранение артефактов, прозрачность процесса.

С учетом задач практики и темы ВКР выбран третий вариант как наиболее полно закрывающий требования к исследовательскому стенду.

### 3.2. Архитектурный состав решения

Практическое решение включает следующие подсистемы:

1. **Веб-приложение-стенд**
   - frontend на React/Vite;
   - backend на Express.

2. **Подсистема генерации тестов**
   - скрипты `generate:test` и `generate:all`;
   - доступ к LLM через OpenRouter API.

3. **Подсистема выполнения/оценки**
   - запуск unit/integration/e2e сценариев;
   - расчет показателей успешности и стабильности;
   - формирование `evaluation-report.json`.

4. **Подсистема поставки и автоматизации**
   - Dockerfile и docker-compose;
   - CI/CD workflow на GitHub Actions.

### 3.3. Обоснование выбора Docker и CI/CD

**Docker** выбран как средство стандартизации окружения и переносимости между локальной машиной и CI runner [1].  
**Docker Compose** выбран для декларативного описания мультисервисного запуска (приложение + генератор тестов) [2].  
**GitHub Actions** выбран как нативный инструмент автоматизации репозитория, поддерживающий:

- многоэтапные workflows;
- артефакты;
- матрицы/входные параметры;
- доступ к контейнерным actions [3], [4].

### 3.4. Практическая значимость решения

Разработанное решение имеет практическую ценность для:

- учебно-исследовательских задач (сравнение моделей и стратегий генерации);
- инженерных задач (ускорение подготовки тестовых заготовок);
- внедрения MLOps-подобных практик в тестировании (артефакты, повторяемость, метрики).

## 4. Реализация и конфигурация тестового стенда

### 4.1. Технологический стек

- `Node.js` и `npm` для сборки/запуска скриптов [5], [6];
- `Jest` для unit/integration тестов [7];
- `Testing Library` для компонентного тестирования [8];
- `Playwright` для E2E-проверок [9];
- `Express` и `React` как основа web-стенда;
- `OpenRouter` для генерации тест-кейсов с помощью LLM [10].

### 4.2. Структура логического процесса

Сквозной сценарий выглядит следующим образом:

1. Выбор модели и типа теста.
2. Генерация тестового файла (или набора файлов).
3. Запуск оценочного процесса.
4. Сохранение структурированного отчета.
5. Публикация результатов в артефакты.

### 4.3. Организация хранения результатов

Результаты генерации/оценки сохраняются в `research-output`:

- сгенерированные тесты;
- метаданные генерации;
- отчет оценки `evaluation-report.json`.

Это обеспечивает последующий анализ, сравнение запусков и репликацию экспериментов.

## 5. Процесс тестирования и методика экспериментов

### 5.1. Категории тестирования

В проекте используются три категории:

1. **Unit** — проверка отдельных компонентов и утилит.
2. **Integration** — проверка API-слоя и взаимодействия модулей.
3. **E2E** — проверка пользовательского сценария в браузере.

Такое разделение соответствует современной практике пирамиды тестирования и позволяет оценивать качество генерации на разных уровнях абстракции [11].

### 5.2. Критерии и метрики оценки

Для оценки автогенерированных тестов применяются:

- наличие корректного тестового файла;
- синтаксическая валидность;
- факт запуска тестов;
- количество успешных/неуспешных прогонов;
- flaky-характеристики (нестабильность между повторами);
- агрегированные показатели pass/fail;
- показатели покрытия (в конфигурациях, где включен расчет покрытия).

### 5.3. Организация сравнения автогенерации и базовых тестов

Для исследовательского сравнения рекомендуется:

1. Зафиксировать набор базовых тестов (эталон).
2. Выполнить генерацию для одной или нескольких моделей.
3. Запускать базовые и автогенерированные наборы в равных условиях.
4. Сравнивать:
   - полноту сценариев;
   - стабильность;
   - долю ложноположительных/ложноотрицательных срабатываний;
   - метрики покрытия.

### 5.4. Воспроизводимость эксперимента

Для воспроизводимости в решении предусмотрены:

- одинаковое контейнерное окружение;
- фиксированная структура директорий результатов;
- автоматизированный запуск в GitHub Actions;
- сохранение артефактов и machine-readable отчета.

## 6. Оформление результата в Docker-образах и конфигурациях

### 6.1. Подготовленные артефакты контейнеризации

В рамках практики созданы:

- `Dockerfile` — образ на базе `node:20-alpine`, содержащий root- и client-зависимости;
- `docker-compose.yml`:
  - сервис `app` для запуска стенда;
  - сервис `test-generator` для генерации тестов;
- `.dockerignore` — исключение лишних директорий и ускорение сборки.

### 6.2. Запуск и эксплуатация

Базовый сценарий:

```bash
npm run docker:build
npm run docker:up
```

Запуск тестов внутри контейнера:

```bash
npm run docker:test
```

Генерация тестов в контейнере:

```bash
export OPENROUTER_API_KEY=<your_key>
npm run docker:generate:test
```

### 6.3. Программные и аппаратные требования

Минимальные требования:

- ОС: Linux/macOS/Windows;
- Docker Engine/Desktop + Docker Compose;
- Node.js 20+ (для локальных скриптов вне контейнера);
- интернет-доступ к OpenRouter;
- аккаунт GitHub и доступ к настройке secrets для CI/CD.

Рекомендуемые ресурсы:

- CPU: от 4 vCPU;
- RAM: от 8 GB;
- свободное место на диске: от 10 GB (с учетом образов и артефактов).

## 7. Поставка на конвейер CI/CD

### 7.1. Общая структура

В репозитории настроены три workflow:

1. `CI` — `.github/workflows/ci.yml`;
2. `CD` — `.github/workflows/cd.yml`;
3. `Generate Tests` — `.github/workflows/generate-tests.yml`.

Это три независимых контура: проверка качества, публикация образа и исследовательский запуск генерации/оценки.

### 7.2. Workflow `CI`

**Триггеры:** `pull_request`, `push` в `main/master`.  
**Назначение:** быстрый quality gate на изменения кода.

Шаги:

1. Checkout.
2. Setup Node.js (cache npm).
3. Установка зависимостей в корне и в `client`.
4. Выполнение тестов (`npm run test`).
5. Сборка frontend (`npm run build`).

Результат:

- подтверждение, что проект не сломан на уровне сборки и базовых проверок.

### 7.3. Workflow `CD`

**Триггеры:** `push` в `main/master`, ручной запуск.  
**Назначение:** выпуск контейнерного артефакта.

Шаги:

1. Checkout.
2. Авторизация в GHCR.
3. Формирование тегов (branch/sha/latest).
4. Build + push через `docker/build-push-action`.

Результат:

- публикация образа в `ghcr.io/<owner>/<repo>`.

### 7.4. Workflow `Generate Tests`

**Триггер:** `workflow_dispatch` с параметрами `model`, `type`, `target`, `generate_all`, `output_dir`.  
**Назначение:** ручной исследовательский запуск с хранением результатов.

Состоит из двух jobs:

1. `generate`
   - проверка секрета `OPENROUTER_API_KEY`;
   - генерация тестов (одна цель или все цели типа);
   - нормализация путей (замена недопустимых символов для корректного artifact upload);
   - загрузка generated-артефакта.

2. `evaluate` (зависит от `generate`)
   - скачивание generated-артефакта;
   - оценка тестов;
   - публикация summary-таблицы в `GITHUB_STEP_SUMMARY`;
   - загрузка `evaluation-report.json`.

### 7.5. Логи, артефакты и верификация

В конвейере реализованы:

- прозрачные логи всех шагов;
- артефакты генерации и оценки;
- summary-метрики в интерфейсе GitHub Actions;
- контроль совместимости путей артефактов для разных файловых систем.

## 9. Ограничения и направления дальнейшего развития

### 9.1. Ограничения текущей реализации

- качество генерации зависит от выбранной модели и промпта;
- полноценное сравнение требует накопления серии прогонов;
- часть показателей покрытия может зависеть от включенных режимов и инфраструктурных ограничений CI.

### 9.2. Направления развития

1. Ввести строгий baseline-набор ручных тестов для статистического сравнения.
2. Добавить матричные прогоны по моделям/температуре/типам целей.
3. Вынести результаты в дашборд (например, агрегированная таблица по экспериментам).
4. Автоматизировать публикацию сравнительных отчетов между запусками.
5. Добавить контроль стоимости/времени генерации как отдельные исследовательские метрики.

В финальную версию рекомендуется включить:

## 11. Заключение

В ходе практики разработано, контейнеризировано и поставлено в CI/CD практическое решение по теме автогенерации тестов для веб-приложений.  
Достигнута ключевая цель: сформирован воспроизводимый инженерно-исследовательский контур «генерация -> запуск -> оценка -> артефакты».  
Решение может быть использовано как основа для экспериментальной части ВКР, включая сравнение моделей, настройку стратегий генерации и количественный анализ качества автогенерированных тестов.
